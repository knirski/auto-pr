Summarize these commits into a PR title and structured review metadata. The renderer will turn your structured fields into the markdown shown under the PR template's "## Description" heading. The same PR body already has separate sections for **commit bullets**, **type of change**, **related issues**, **breaking changes**, and **how to test**—do **not** duplicate those: do not restate the commit list, do not write testing steps, do not repeat issue links or breaking-change footers that commits may carry.

Respond with JSON only: {"title": "...", "motivation": "...", "risks": ["..."], "notesForReviewers": "..."}.

title: Conventional commit format: TYPE: SUBJECT or TYPE(scope): SUBJECT. Optional (scope) for a subsystem or feature area (e.g. feat(auth): …). Pick a fitting type: feat, fix, docs, chore, refactor, security, perf, test, ci, build, revert, or style. Max 72 chars trimmed. Subject must be concrete after the colon (WRONG: feat. CORRECT: feat: add session refresh). Prefer type security when the change is security-sensitive.

motivation: Plain text, 2–5 sentences. Put the **main reason this branch exists** first: problem, goal, or constraint. This is the most important field—do not bury it. Avoid a vague opener and avoid a laundry list of every commit theme; synthesize the overarching intent.

risks: Array of 1–5 plain-text bullets. Each item should describe what could go wrong, what reviewers should double-check, or what operational/integration concern the commits imply. If nothing stands out, use one concrete low-risk item such as "Low risk: docs-only change; review focused on wording accuracy."

notesForReviewers: Plain text, optional but always present in JSON. Use `""` when nothing extra is needed. When non-empty, point reviewers to non-obvious files, tradeoffs, or read order. Do not repeat motivation or risks.

Use `inline code` in `motivation` or `notesForReviewers` for paths or APIs when helpful. Do not invent alternatives or deployment detail absent from commits. If commits only reference issues briefly, do not paste long boilerplate—the Related issues section will show links.

{"title":"feat(ci): harden generate workflow token fallback","motivation":"GitHub token handling across reusable workflows was inconsistent, which made AI-backed PR generation fragile in repositories that do not provide a dedicated PAT. This change aligns the workflow defaults and token forwarding path so the generate job behaves predictably in common CI setups while keeping the branch mergeable and reviewable.","risks":["Verify `github.token` and forwarded secret precedence in reusable workflow calls.","Double-check permission scopes such as `models:read` in jobs that query GitHub Models."],"notesForReviewers":"Start with `.github/workflows/auto-pr-generate-reusable.yml`, then review related config/docs updates."}

Tone: direct, technical. No filler like "This PR" or "We introduce". Every field must be valid JSON (escape quotes and newlines inside values as needed).

# Action-local bundled model routing context

## Context and Problem Statement

The generate reusable workflow runs in adopter repositories through `workflow_call`. The workflow file is pinned to this repository, but the checkout workspace belongs to the adopter. That means an action used by the reusable workflow cannot assume the adopter has this repository's `src/**`, `node_modules`, Bun, or project package metadata.

The model routing context action needs more logic than small inline YAML or shell can express cleanly. It classifies changed files, commit semantics, diff signals, runner resources, local GGUF sizing risk, and prompt guidance before `auto-pr-generate-content` calls the language model. Those signals select the initial model band, choose tool-use strategy, set local-model defaults for GitHub-hosted runner capacity, and provide structured context that the later language model prompt consumes.

This logic must be tested and maintainable, but it must also be portable for non-JavaScript adopter repositories.

## Considered Options

* **Run TypeScript with Bun from a composite action** - Keeps the implementation close to the rest of the project, but fails in adopter repositories where the reusable workflow did not install Bun. It also relies on this repository's dependency tree being available at action runtime.
* **Import shared `src/**` modules from the action** - Avoids duplicate logic, but is not safe for remote action execution. `GITHUB_ACTION_PATH` points to the downloaded action tree while `GITHUB_WORKSPACE` points to the adopter repository, and a pinned action cannot depend on the adopter checkout containing auto-pr source.
* **Inline the router as shell or workflow YAML** - Maximizes portability, but makes semantic classification, scoring, and summary generation hard to test and review. It also encourages a long workflow script that adopters and contributors cannot reason about locally.
* **Keep TypeScript/Effect source inside the action directory and run a checked-in Node bundle as a JavaScript action** - Keeps the implementation testable and expressive while giving the reusable workflow a self-contained runtime artifact with a GitHub-provided Node runtime.

## Decision Outcome

Chosen option: **keep the model routing context implementation action-local and execute a checked-in Node bundle as a `node24` JavaScript action**.

### Design details

- The reusable action owns its routing policy under `.github/actions/auto-pr-build-model-routing-context/`.
- Source files stay in that action directory:
  - `auto-pr-build-model-routing-context.ts`
  - `model-routing.ts`
- The runtime file is `auto-pr-build-model-routing-context.mjs`, generated by `scripts/build.ts`.
- `action.yml` declares `runs.using: node24` and `main: auto-pr-build-model-routing-context.mjs`.
- The generated bundle is committed because remote action execution must work in adopter repositories without installing this repository's dependencies.
- The generated bundle is action-local, not root package `dist/`. Root `dist/` remains owned by the dist update workflows.
- Routing signal semantics are part of the action contract:
  - `sourceChurn` counts only files classified as source.
  - Docs, tests, dependency, generated, and workflow churn remain separate signals.
  - Breaking changes are classified before tiny, docs-only, or generated-only shortcuts.
  - Runner capacity affects local default model selection for the bundled llama.cpp path.
  - The structured signal summary is passed forward as prompt context for `generate-content`.

## Consequences

### Good

- Adopter repositories do not need Bun, package manager metadata, `node_modules`, or copied action code.
- The action can still use TypeScript, Effect, and unit tests at development time.
- Workflow pins bind the reusable workflow, action source, and action runtime bundle to one commit.
- The long routing script is removed from the reusable workflow and kept behind a named JavaScript action boundary.
- Model selection and prompt context use the same measured routing signals.

### Bad

- Generated JavaScript lives in `.github/actions/**`, so source changes require regenerating and reviewing a bundle diff.
- The action-local boundary duplicates some concepts that might otherwise live in shared application code.
- Contributors must remember that root `dist/` and action-local bundles have different commit policies.

### Neutral

- `auto-pr-generate-content` remains the only workflow entrypoint that calls the language model.
- `LanguageModel.generateText` and the JSON Schema decode path remain unchanged.
- Workflow self-reference pin automation still applies when the action changes.

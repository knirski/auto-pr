# auto-pr Documentation Website — Design Spec

## Overview

A Starlight (Astro) documentation site with a custom landing page, deployed to GitHub Pages via CI. The site serves two purposes: a marketing-style homepage explaining what auto-pr does, and a documentation hub sourced from the existing `docs/` directory.

## Tech Stack

- **Static site generator:** Starlight (Astro)
- **Package manager / build runner:** Bun
- **Deployment:** GitHub Pages via `actions/deploy-pages@v4` (artifact-based, no `gh-pages` branch)

## Project Structure

## Content Pipeline

### Source of truth

All documentation lives in `docs/` at the project root. The `website/` directory never contains authoritative markdown — only generated copies.

### Copy script (`scripts/copy-docs.ts`)

Runs before every dev server start and production build. Does three things:

**1. Frontmatter injection** — Reads the first `# Heading` from each file and uses it as the Starlight `title`. A static mapping provides sidebar order and optional label overrides:

| Source file | Sidebar label | Order |
|---|---|---|
| `INTEGRATION.md` | Getting Started | 1 |
| `TROUBLESHOOTING.md` | Troubleshooting | 2 |
| `PR_TEMPLATE.md` | PR Template Placeholders | 3 |
| `ARCHITECTURE.md` | Architecture | 10 |
| `CI.md` | CI & Workflows | 11 |
| `WORKFLOW_SECURITY.md` | Workflow Security | 12 |
| `CII.md` | CII Best Practices | 13 |

ADR files are auto-ordered by their existing numeric filename prefix.

**2. Link rewriting** — Transforms relative markdown links to Starlight paths:
- `[CI docs](CI.md)` → `[CI docs](/docs/ci/)`
- `[ADR-001](adr/001-some-decision.md)` → `[ADR-001](/docs/adr/001-some-decision/)`
- External URLs and anchor links are left untouched.

**3. File placement** — Flat docs go to `src/content/docs/`, the `adr/` subdirectory is preserved:
- `docs/INTEGRATION.md` → `src/content/docs/integration.md`
- `docs/adr/001-extract.md` → `src/content/docs/adr/001-extract.md`

Filenames are lowercased. `docs/adr/README.md` becomes the ADR index page.

### Files excluded from the site

| File | Reason |
|---|---|
| `README.md` | Content covered by the landing page |
| `CONTRIBUTING.md` | Workflow-specific (Nix, pre-push hooks, local CI). Linked from site, not copied. |
| `CHANGELOG.md` | Link to GitHub releases instead |
| `AGENTS.md` | Agent-specific, not useful as docs |

## Landing Page (`src/pages/index.astro`)

A custom Astro page (not part of Starlight's docs routing) with three sections:

### Section 1: Hero
- Project name and tagline: "AI-powered pull requests from conventional commits"
- One-sentence value prop mentioning `ai/*` branches
- Two CTAs: "Get Started" (links to `/auto-pr/docs/getting-started/`) and "View on GitHub"

### Section 2: Feature Cards
Four cards in a 2x2 grid:
- **Zero Config** — Convention over configuration, works with any GitHub project
- **AI Descriptions** — Multi-commit PRs get AI-generated summaries
- **Template Aware** — Automatically fills PR template placeholders
- **Secure by Design** — Two-phase workflow separates generation from PR creation

### Section 3: Quick Start
- The `npx -p github:knirski/auto-pr auto-pr-init` command
- A short push-to-branch example showing the end-to-end flow
- Visual indication of the automatic PR creation

## Starlight Configuration

```js
// website/astro.config.mjs
import { defineConfig } from 'astro/config';
import starlight from '@astrojs/starlight';

export default defineConfig({
  site: 'https://knirski.github.io',
  base: '/auto-pr',
  integrations: [
    starlight({
      title: 'auto-pr',
      social: {
        github: 'https://github.com/knirski/auto-pr',
      },
      customCss: ['./src/styles/custom.css'],
      editLink: {
        baseUrl: 'https://github.com/knirski/auto-pr/edit/main/docs/',
      },
      sidebar: [
        {
          label: 'User Guide',
          items: [
            { slug: 'getting-started' },
            { slug: 'troubleshooting' },
            { slug: 'pr-template' },
          ],
        },
        {
          label: 'Contributing',
          items: [
            { slug: 'architecture' },
            { slug: 'ci' },
            { slug: 'workflow-security' },
            { slug: 'cii' },
          ],
        },
        {
          label: 'ADRs',
          autogenerate: { directory: 'adr' },
        },
      ],
    }),
  ],
});
```

## CI/CD Workflow

New workflow at `.github/workflows/deploy-pages.yml`:

```yaml
name: Deploy website

on:
  push:
    branches: [main]
    paths:
      - 'docs/**'
      - 'website/**'

permissions:
  contents: read
  pages: write
  id-token: write

concurrency:
  group: pages
  cancel-in-progress: true

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@de0fac2e4500dabe0009e67214ff5f5447ce83dd # v6.0.2
      - uses: oven-sh/setup-bun@0c5077e51419868618aeaa5fe8019c62421857d6 # v2.2.0
      - run: bun install
        working-directory: website
      - run: bun run build
        working-directory: website
      - uses: actions/upload-pages-artifact@7b1f4a764d45c48632c6b24a0339c27f5614fb0b # v4.0.0
        with:
          path: website/dist

  deploy:
    needs: build
    runs-on: ubuntu-latest
    environment:
      name: github-pages
      url: ${{ steps.deploy.outputs.page_url }}
    steps:
      - id: deploy
        uses: actions/deploy-pages@cd2ce8fcbc39b97be8ca5fce6e763baed58fa128 # v5.0.0
```

### Path filter
Only rebuilds when `docs/` or `website/` change — code-only pushes to main skip the deploy.

### Prerequisites
GitHub Pages must be enabled in repo settings with Source set to "GitHub Actions".
